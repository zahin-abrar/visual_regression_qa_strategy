### Questions to answer

1. Which variables are required, optional or obsolete?
2. Which values are safely hardcoded defaults?
3. Which settings belong to the Python runner, and which belong to the Expo application or Metro?
4. Which settings are read at process startup, application build time or runtime?
5. Are any variables secrets?
6. Is configuration precedence predictable?
7. Are conflicting or invalid values rejected clearly?
8. Can local PyCharm execution work without creating an `.env` file?
9. Can a future CI pipeline supply the configuration using job environment variables?
10. Is the current Git ignore policy sufficient to prevent local secrets and machine-specific configuration from being committed?

### Configuration recommendation

Prefer the simplest correct solution.

If existing environment variables and defaults are sufficient, do not introduce an `.env` dependency.

Consider adding an `.env.example` only if it materially improves documentation. If introduced:

- Use placeholder or safe example values only.
- Never include real credentials or machine-specific secrets.
- Explain whether the file is merely documentation or actually loaded.
- Preserve Git ignore protection for real `.env` files.
- Do not make an optional `.env` file mandatory.

Do not install `python-dotenv` or another package unless a verified requirement justifies it.

For future CI/CD, document how configuration would be supplied by the pipeline and distinguish non-sensitive variables from secrets.

Do not create a CI workflow as part of EXEC-036.
