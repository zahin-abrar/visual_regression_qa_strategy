
EXEC-042C — GitHub Actions Emulator Boot and Log Collection Remediation

PROJECT
D:\Projects\visual_regression_qa_strategy

Branch: main
Last locally reported commit: 18db02a

OBJECTIVE

Fix the infrastructure failures observed during the first
GitHub execution of the independent Android visual-test
workflow.

Ensure that diagnostic log collection cannot hang when
emulator initialization fails.

Do not rebuild the Android APK or change visual-test behavior.

BACKGROUND

The visual-only GitHub Actions workflow successfully reached
the Android emulator provisioning stage.

Workflow:
.github/workflows/android-visual-tests.yml

The following stage completed:
Setup 3/5: Appium and UiAutomator2 (pinned)

The following stage failed:
Setup 4/5: boot headless emulator
(API 37, 1080x2424, 420 dpi)

Observed errors:

1. Emulator executable failed to load:

   error while loading shared libraries:
   libpulse.so.0: cannot open shared object file

2. AVD creation failed:

   Error: No device found matching --device pixel_10

3. Fallback AVD creation also failed:

   Error: No device found matching --device pixel_9

The workflow never reached APK installation, application
startup or pytest.

A second problem was observed during cleanup:

The "Collect final logs" step remained active for more
than 12 minutes after emulator provisioning failed.

Its commands were:

adb logcat -d -t 4000 > "$LOG_DIR/logcat-tail.txt" 2>&1 || true

bash .github/scripts/disk-report.sh "visual job end" \
  > "$LOG_DIR/disk-report.txt" 2>&1 || true

The exact blocking command has not been confirmed.

The user was advised to cancel the workflow rather than
continue waiting indefinitely.

Treat both issues as infrastructure problems, not
visual regression failures.

TASK B — MISSING LINUX LIBRARY

The emulator requires libpulse.so.0, which is not
available in the current GitHub runner environment.

1. Add a bounded dependency installation step before
   emulator execution.

2. Install the appropriate Ubuntu 24.04 package,
   expected to be libpulse0.

3. Verify the required library is resolvable.

4. Preserve the existing SDK, emulator image and
   Android environment.

5. Do not broadly upgrade or replace system packages.

6. Ensure package installation failures remain genuine
   workflow failures.

TASK C — AVD DEVICE PROFILE SELECTION

The Android SDK's avdmanager did not recognize either:

pixel_10
pixel_9

These names must not be assumed to exist.

1. Inspect the current AVD creation implementation.

2. Use avdmanager list device to identify available
   device definitions at runtime.

3. Select a reliable supported phone definition,
   or create the AVD without an explicit device profile
   if supported by the installed tooling.

4. Prefer deterministic configuration over complicated
   fallback chains.

5. Preserve:
   - Android API 37
   - Existing x86_64 system image
   - 1080x2424 display
   - 420 dpi
   - Headless operation
   - Cold boot
   - KVM acceleration
   - Existing emulator readiness checks

6. Verify the configured AVD was actually created.

7. Fail clearly if the selected system image or
   required emulator dependencies are unavailable.

8. Ensure all AVD creation errors propagate correctly.

Do not silently switch Android API levels.

TASK D — PREVENT CLEANUP HANGS

The "Collect final logs" step exceeded 12 minutes
after emulator setup failed.

Investigate both commands rather than assuming the
ADB command was definitely responsible.

1. Inspect the final log-collection step.

2. Ensure all potentially blocking diagnostic commands
   have explicit execution time limits.

3. Before requesting logcat, check whether an Android
   device is available.

4. Do not rely on an unbounded adb devices request;
   the availability check must also have a timeout.

5. Use a short timeout, approximately 10 seconds,
   for ADB logcat collection.

6. Avoid commands that implicitly wait indefinitely
   for a device to become available.

7. Keep disk reporting, but ensure it is also bounded
   if it invokes potentially blocking subprocesses.

8. Preserve diagnostic output whenever available.

9. If a device is unavailable, write a clear explanatory
   note to the log output rather than treating missing
   logcat as another workflow failure.

10. Preserve best-effort cleanup behavior.

11. Ensure failures during diagnostics do not mask
    the original emulator provisioning failure.

12. Ensure artifact-upload steps remain reachable
    after infrastructure failures.

13. Avoid introducing lengthy sleeps or automatic retries.
