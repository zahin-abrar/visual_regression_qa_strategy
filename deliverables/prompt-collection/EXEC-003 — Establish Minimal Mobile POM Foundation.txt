## Step 2 — Implement minimal POM

Establish only the abstractions needed for our approved scenario.

### Screen Object: `HomeScreen`

Responsibilities:

- Access the article-card component.
- Encapsulate screen-level locators or navigation only when necessary.

### Component Object: `ArticleCard`

Responsibilities:

- Locate the article card using existing React Native accessibility identifiers.
- Wait for an explicit UI-ready condition.
- Access the article title.
- Capture the actual article-card element screenshot.

The current app is expected to expose `qa-article-card-ready` and `qa-article-title`. Inspect the existing code before selecting locators.

Do not assume the ready element contains the full visual bounds of the card. If element boundaries cannot be established without a live session, defer that verification to the native-capture task.

### Driver configuration

Keep existing Android UiAutomator2 session configuration in its current module or a small dedicated driver module.

Do not introduce generic abstractions unnecessarily.

### Visual comparison

Preserve the existing image comparison implementation and baseline paths. Keep visual assertions separate from Screen and Component Objects.

## Architectural rules

1. Tests define scenarios and assertions.
2. Screen Objects encapsulate screen behavior.
3. Component Objects encapsulate reusable UI elements.
4. Drivers isolate platform-specific session configuration.
5. Visual utilities own image comparison and diff generation.
6. App fixtures remain independent of Appium.

Avoid:

- Complex inheritance hierarchies.
- Unused base classes.
- Speculative iOS implementations.
- New dependencies without demonstrated necessity.
- Arbitrary sleeps.
- Hard-coded golden regeneration inside tests.
