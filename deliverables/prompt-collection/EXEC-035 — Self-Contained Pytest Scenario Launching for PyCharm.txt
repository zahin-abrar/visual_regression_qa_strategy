PHASE B — IMPLEMENT THE MINIMUM CHANGE

Preferred design, if compatible with the current architecture:

- Each visual test explicitly declares its scenario.
- A shared pytest fixture or existing launcher reads that declaration.
- The launcher constructs the correct development-client URL.
- The application is cold-launched with that scenario.
- The test proceeds only after the existing identity/readiness assertions.

A registered pytest marker such as:

@pytest.mark.qa_scenario("breaking_news")

is acceptable, but inspect the current design before choosing the implementation.

Avoid filename-based magic or duplicated launch URLs across test files.

Ensure the five normal scenarios map correctly:
- long_headline
- breaking_news
- dark_article
- no_image
- empty_feed

The intentional-failure test must request breaking_news through the same mechanism.

It must retain @pytest.mark.intentional_failure and must NOT acquire the normal visual marker.

Register any new pytest marker in pytest.ini.

Keep the existing scenario-launch implementation and development-only fixture gate.

Allow external host/port overrides where genuinely useful for CI or different environments, but do not require callers to supply a complete scenario-specific launch URL.

If the existing VVP_QA_LAUNCH_URL override is retained for compatibility, validate it against the declared scenario and fail clearly on conflicts. A stale environment variable must not silently select the wrong fixture.

If the investigation reveals that this requires a broad fixture redesign, stop and report the findings rather than starting a large refactor.
