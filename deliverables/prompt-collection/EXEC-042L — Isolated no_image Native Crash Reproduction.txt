## 2. Established evidence

The latest full-suite GitHub-hosted execution produced:

| Scenario | Result | Changed pixels |
|---|---|---|
| `breaking_news` | PASS | 0 |
| `dark_article` | PASS | 0 |
| `empty_feed` | PASS | 0 |
| `long_headline` | PASS | 0 |
| `no_image` | FAIL | Comparison not reached |

**Pytest:** 4 passed, 1 failed, 130 deselected.

All four successful scenarios completed actual golden comparisons.

The `no_image` failure occurred during scenario initialization, before screenshot comparison.

### Native crash

Android logcat reported at approximately 17:38:51 UTC on November 9, 2026:

```text
Fatal signal 11 (SIGSEGV)
Code: SEGV_ACCERR
Process: de.volksverpetzer.app
Thread: mqt_v_js
Page size: 16384 bytes

Cause: trying to execute non-executable memory.
```

The native stack included:

```text
libreactnative.so

facebook::react::MountingCoordinator::pullTransaction
facebook::react::FabricUIManagerBinding::schedulerDidFinishTransaction
facebook::react::Scheduler::uiManagerDidFinishTransaction
```

Further observations:

- JavaScript startup occurred about two seconds before the crash.
- No confirmed `status=active id=no_image` or `marker rendered qa-scenario:no_image` event was present.
- The Android launcher was foregrounded after the crash.
- The application process was no longer running.
- The Expo onboarding overlay was not detected.
- Previous full-suite execution also recorded a similar native crash during `no_image`.

### What remains unproven

We do not know whether:

1. The `no_image` fixture or its rendering triggers the crash.
2. The fifth consecutive application launch contributes to the crash.
3. Repeated Appium sessions create problematic native lifecycle state.
4. The Android 16 KB system image contributes to the crash.
5. Host or guest resource pressure contributes to the crash.

Do not promote any of these hypotheses to confirmed root cause without evidence.
