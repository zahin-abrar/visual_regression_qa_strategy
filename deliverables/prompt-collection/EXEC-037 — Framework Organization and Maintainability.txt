## Phase E — Targeted duplication reduction

After inspecting actual repeated code, implement the smallest sensible abstraction.

Potential candidates include:

- Artifact directory preparation.
- Golden path resolution.
- Native screenshot capture and metadata saving.
- Comparison and metrics output.
- Diagnostic collection.
- Driver lifecycle cleanup.
- Common screenshot readiness verification.

These are candidates, not a mandate to create a single large abstraction.

### Design principles

1. Keep each test's scenario selection explicit.
2. Preserve scenario-specific assertions in the test file.
3. Make tests readable without requiring developers to navigate many helpers.
4. Use shared fixtures or helpers for genuine infrastructure responsibilities.
5. Avoid highly parameterized generic test engines for only five scenarios.
6. Avoid new inheritance layers or unnecessary page-object restructuring.
7. Preserve precise error messages and diagnostic artifacts.
8. Keep the intentional-failure test's special reference selection explicit.

The intentional-failure test must still compare a real application screenshot against its deliberately incorrect reference and fail with a genuine assertion.

Do not replace its failure with `xfail`, `skip`, a mocked comparator or an inverted passing assertion.

### Behavioral invariants

Preserve:

- Appium UiAutomator2 driver/session creation.
- Pre-render scenario selection and cold-launch isolation.
- Scenario identity checks.
- UI readiness checks.
- Native element screenshot capture.
- Scenario-specific assertions.
- Comparison thresholds.
- Golden profile selection.
- Screenshot dimensions and crop behavior.
- Actual, context, diff, JSON and diagnostic artifact generation.
- Session termination and driver cleanup.
- Configuration overrides and validation behavior.

Investigate the known difference in tolerance-override handling between `breaking_news` and the other four tests.

Report whether it is deliberate or accidental.

Do **not** change effective comparison thresholds or comparison policy during this refactor. If consistency would require behavioral changes, document the recommendation separately.
